# v0.19.15 — Saved onsite photos in the mobile app

## Fix

The dispatcher image already used an authenticated JSON request returning a JPEG data URI. Saved onsite photos used protected HTTP URLs directly in the native Image component. This release removes that separate native image-authentication/cache path for onsite evidence.

The app now retrieves each stored front ID, optional back ID and VIN photo through the normal authenticated API client. The backend reuses the existing evidence reader, including tenant authorization, encrypted-file decryption and custody-view logging, and returns the identical JPEG bytes as a base64 data URI. The native Image component receives image data, not a URL requiring another authenticated image request. The existing broker/browser binary image endpoints remain unchanged.

No existing photos need to be retaken or re-uploaded. No stored image is rewritten, no QA is rerun, and release/confirmation/custody state remains intact. The local neural VIN reader from v0.19.14 is unchanged.

## Loading and retry behavior

- Saved front/back/VIN previews reload when reopening an active or released load. Local accepted captures remain the preview until navigation/assignment change/sign-out clears the drafts as before.
- Each image has a loading indicator and its own failure message. A failed photo does not hide the others. Reload saved photos retries the saved previews without resubmitting or changing a release.
- If a retained local capture can no longer render, the photo component can fall back to the protected saved data for that same image. Failed images show an error instead of staying as a blank white box.
- Old two-photo attempts load front and VIN normally; no nonexistent optional back photo is requested.
- Returned shipment, attempt, revision and image-kind metadata must match. Non-image URLs, malformed data and late results after switching loads/logins are not rendered. Image data is kept in app memory and cleared with the selected context; this adds no persistent on-device photo cache.
- Saved-photo reads are sequential because each records a custody view. API responses are private/no-store. Authorization tokens are never placed in photo URLs or image sources.

## Apply the complete update

Preserve your .env and Docker volumes. Copy the ZIP's inner ValhallaFreight contents over C:\GitHub\ValhallaFreight, including backend/app and safe-load-mobile. The ZIP contains project source, not your live database or identity photos. Existing Compose, migrations, document volumes and OCR dependencies are unchanged.

Stop the OLD Metro PowerShell window with Ctrl+C, then run:

```powershell
Set-Location C:\GitHub\ValhallaFreight
docker compose -p valhallafreight up -d --build
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\safe-load-mobile\Start-SafeLoad.ps1 -ComputerIP 192.168.1.195
```

Keep Docker running. Scan the new QR on the phone, or press **a** in Metro with the Android emulator already running. Verify **App v0.19.15**. TMS server URL remains http://192.168.1.195:8000 unless the PC's IP changed. Both backend and app must be updated because this version adds a protected preview endpoint.

Open an existing Released load and scroll through Front ID, Back ID (if submitted) and VIN. If an old screen remains, use Reload saved photos or return to the queue and reopen the load. Do not resubmit/release the shipment just to reload its pictures. Also test an active load, a two-photo older attempt, leaving/reopening a load, pull-to-refresh and signing out.
