# Valhalla Freight v0.4.0 — Customer 360

Customer 360 is the first feature built using the modular domain structure that Valhalla Freight will use going forward.

## Functional scope

- Customer account list with search and account-level KPIs
- New customer creation
- Customer 360 detail workspace
- Overview, Locations, Contacts, Commercial, and Activity tabs
- Customer locations with LTL operating attributes
- Customer contacts with operational/billing/quote roles
- Customer notes and activity timeline
- Customer shipment history
- Account ownership, billing address, payment terms, credit limit and pricing defaults
- Seeded Customer 360 data for the existing development customers

## Backend domain organization

`backend/app/domains/customers/`

- `models.py` — Customer 360 supporting database tables
- `schemas.py` — Pydantic request/response contracts
- `service.py` — Customer business logic and database orchestration
- `routes.py` — FastAPI endpoints only

The original `customers.py` route remains only as a compatibility shim.

## Frontend feature organization

`frontend/src/features/customers/`

- `types.ts` — Customer TypeScript contracts
- `api.ts` — Customer API calls
- `useCustomer360.ts` — Customer-specific data hook
- `CustomersPage.tsx` — customer list page entry
- `CustomerDetailPage.tsx` — detail page entry
- `components/CustomerList.tsx`
- `components/CustomerDetail.tsx`
- `components/CustomerModal.tsx`

This prevents Customer 360 from becoming part of a giant shared `Tables.tsx` file.

## Database upgrade behavior

v0.4.0 adds new tables rather than altering the existing `customers` table:

- `customer_profiles`
- `customer_locations`
- `customer_contacts`
- `customer_activities`

Because these are additive tables, the current development PostgreSQL volume can be preserved. `Base.metadata.create_all()` creates the new tables at startup.
