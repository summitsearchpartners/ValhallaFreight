# Valhalla Freight v0.8.2 — Secure Adapter Credentials

## Purpose
v0.8.2 moves carrier API authentication into the Valhalla Freight Integration Hub so administrators can configure carrier connections without editing source code or committing secrets to GitHub.

## Security model
- Credentials are submitted over the authenticated Valhalla backend API.
- Secrets are encrypted before being stored in PostgreSQL.
- Saved passwords, API keys, bearer tokens, and client secrets are never returned to the browser.
- The UI only receives masked hints and boolean credential-status flags.
- `INTEGRATION_SECRET_KEY` is the backend-only encryption root. Set it once before production and do not rotate it without a credential migration plan.
- Existing Dayton `.env` credentials remain supported as a backward-compatible fallback, but Integration Hub credentials take precedence.

## Dayton Freight
The Dayton adapter can now be configured entirely from Administration → Integration Hub → Dayton Freight:
- API base URL
- Environment
- Username
- Password
- Customer account
- Freight terms
- Direct-only preference

The Test Dayton Authentication button uses the stored encrypted credentials. Quote Studio live Dayton rating and Shipment Control Tower Dayton tracking use the same secure credential source.

## OpenAPI onboarding
OpenAPI import now also records:
- published server/base URLs
- published authentication/security schemes
- detected authentication type

Imported provider candidates can be opened with Manage and configured with common authentication methods including Basic Auth, API Key, Bearer Token, and client credentials. A carrier-specific normalization adapter is still required before operational live calls are enabled.
