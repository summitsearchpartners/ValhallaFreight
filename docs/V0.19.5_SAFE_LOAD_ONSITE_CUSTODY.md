# v0.19.5 — Onsite phone camera, broker release and custody snapshots

## Install both desktop and mobile source

Keep the existing .env, PostgreSQL data volume and document volume. Copy the inner ValhallaFreight project contents over C:\GitHub\ValhallaFreight, including safe-load-mobile. Do not replace only the frontend/backend: an old mobile folder can keep serving the old interface.

Stop the old Expo/Metro PowerShell window with Ctrl+C. In a separate PowerShell window:

```powershell
Set-Location C:\GitHub\ValhallaFreight
docker compose -p valhallafreight up -d --build
```

After Docker finishes, use a separate PowerShell window:

```powershell
Set-Location C:\GitHub\ValhallaFreight\safe-load-mobile
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-SafeLoad.ps1 -ComputerIP 192.168.1.195
```

The launcher prints the mobile package version and source folder, installs the pinned dependencies and clears the Metro cache. Open Expo Go SDK 58 on Android and scan the new QR code. In Safe Load use server http://192.168.1.195:8000 and the Manufacturer credentials. Verify the sign-in/queue header says App v0.19.5. If not, the phone is still opening an older Metro project. Close the old project and scan this window's new code. Existing local-network firewall rules for ports 8000 and 8081 apply. Keep Docker and Metro running and the PC awake.

The project contains one additive custody table. Startup creates it without resetting existing data. Existing migration files and Compose volume configuration are unchanged. Never run docker compose down -v. Refresh desktop with Ctrl+F5.

## Why the camera buttons were missing

The previous app hid capture controls until the backend reached awaiting_verification. A newly dispatcher-submitted load could therefore show the license but no onsite capture controls. v0.19.5 displays prominent TAKE ONSITE DRIVER ID PHOTO and TAKE ONSITE TRUCK VIN PHOTO buttons at the top of every active hold, including pending dispatcher review and rejected arrivals. Released/cancelled loads do not allow new capture. The phone opens its native camera; there is no saved-photo picker in the warehouse app.

Capture can start while waiting for a dispatcher. Submission requires a complete dispatcher assignment, both onsite photos and the configured broker phone. A changed assignment clears the phone's old captures and requires new photos. If the assignment changes during a camera capture, that capture is rejected as stale.

## Normal first-arrival flow

1. Broker creates the shipment and carrier invitation. Dispatcher submits driver identity, license photo and truck VIN. Broker saves the monitored phone under Warehouse escalation contact. There is no mandatory extra broker-approval click before the first photo verification in this workflow.
2. Manufacturer warehouse employee opens the unreleased test load in the app. Tap the prominent onsite ID camera button, take the photo, then take the actual truck VIN photo. Include clear printed name, license number, issuing state and expiration; a sharp PDF417 image of the ID back can also supply the ID fields.
3. Inspect both previews and visually compare the arriving person and physical ID with the dispatcher photo. Turn on the visual-match confirmation only if it matches. Leaving it unchecked submits a rejection for broker review rather than granting release.
4. Press SUBMIT · VERIFY & RELEASE below the previews. The server reads the actual uploaded pictures locally using Tesseract and barcode decoding. A readable match records a confirmed verification, releases the hold and sets the shipment to in_transit, with pickup/transit tracking and a confirmed popup in the app. The header reads RELEASED — IN TRANSIT.

The mobile workflow uses camera photographs and one submission. Desktop retains its barcode-scanner alternative. Initial photo verification does not require prior broker approval, but a rejection cannot be cleared automatically by uploading a matching retry.

## Rejection and broker callback

- The app shows REJECTED — DO NOT RELEASE and a popup with the configured broker number, Call broker and Keep on hold. A critical in-software broker notification is saved in the same rejection transaction.
- If the warehouse has not submitted both photos yet (for example it used the explicit visual-mismatch report), it can still photograph and submit both as evidence while rejected. The hold remains. The broker needs both current onsite images before authorizing release.
- Broker/Super Admin opens Notifications → Review rejection & authorize release. The Safe Load popup shows the rejected evidence and the Broker verification & release authorization form. The broker independently verifies the driver and truck through the known carrier/warehouse contact, checks all three confirmation boxes, and records at least 20 characters of callback/verification notes.
- Confirm verified driver & release for transit records a manual broker authorization, releases the hold and updates the shipment to in_transit. The previous rejected OCR/photo attempt remains rejected in the audit history and is labeled as a historical check. It is not rewritten as an automatic match.
- Manufacturer accounts cannot use the broker-release API. Unrelated broker companies cannot access it. Stale assignment versions or rejection IDs are refused; the broker must refresh and review new evidence first. Cancelled/released loads cannot be overridden through this action.
- The foreground phone app refreshes about every three seconds and shows the release with a confirmation popup and the releasing broker account. No additional warehouse release tap is required after broker authorization. Background push/SMS is not included.
- Alternatively, a broker may correct the dispatcher assignment or approve a corrected assignment for another warehouse verification; versioning and the existing hold checks remain in place.

## Chain of custody

The system records authenticated account identity, name/role, server UTC timestamps, assignment revision, phase, driver name, masked license metadata, VIN, approval/verification/release account IDs, broker contact, decision reason and references/hashes for evidence. Capture-event records identify the signed-in employee reporting each onsite camera shot. Device camera times and capture-source labels are explicitly recorded as client-declared metadata; the server time and authenticated account are authoritative for receipt. Individual staff accounts are needed to distinguish individual people; a shared login identifies only that shared account.

Every new hold and subsequent operational phase generates a structured snapshot. Dispatcher photos are versioned into retained encrypted custody storage before a later assignment replaces the active picture. Arrival photos remain encrypted in the existing document volume. Failed attempts remain available alongside subsequent broker decisions.

Custody snapshots are append-only through the application, including blocked ORM bulk edits/deletes. Each snapshot contains a SHA-256 link to the previous one, and evidence hashes are checked when viewing/exporting the chain. The exported JSON contains redacted storage paths and can independently verify the state hash chain. Authorized users can view the phase snapshots in desktop and mobile; desktop offers Export chain of custody. This is application-level audit evidence, not externally notarized proof. Database/storage owners still control the underlying infrastructure. Existing backups and an owner-defined retention policy remain necessary; the release does not silently delete custody evidence.

Snapshots begin at this version's installation and subsequent activity. Earlier events remain in the original event log. Historical snapshots or missing pre-update evidence are not fabricated. Startup does not backdate custody records.

## Verification limits and local test

OCR matches extracted ID fields and VIN plus the warehouse operator's visual comparison. It does not authenticate a license with the DMV, perform automated facial recognition/liveness or verify VIN ownership. The inherited conservative OCR layout rules remain: unsupported/ambiguous fields fail closed and route to broker review. Test actual Android cameras, lighting and real license layouts before a pilot. No physical phone was available during this implementation.

Use an unreleased fictional load and the plain TEST DOCUMENT pictures in docs/safe-load-test-photos. Set dispatcher John Doe, license TEST1234, state KS, expiration 2030-01-01 and VIN 1HGCM82633A004352. Set a monitored broker phone for your local test. Photograph the fictional ID and VIN from a printed page or another display. For rejection, use the wrong-vin picture, then exercise the broker notification action. The warehouse app should switch to RELEASED — IN TRANSIT without restarting. These are workflow fixtures, not valid identity documents.
