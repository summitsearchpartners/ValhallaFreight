## One onsite capture section

A load shows its dispatcher reference photo and VIN, followed by the shared Broker call card and ONE **Onsite capture · 2 photos required** section. The redundant top camera panel is removed. The broker contact is shown before any capture and remains available after a decision. Missing contact setup shows a visible warning card; Broker Admin must save the monitored name/phone under My Profile → Safe Load call contact.

1. Take the arriving driver's physical ID photo.
2. Take the arriving truck's VIN-label photo.
3. If printed text is hard to extract, use **Scan back of driver license · PDF417**. The camera reads the physical ID barcode and the server returns a preview of name, issuing state, license ending, expiration and DOB when encoded. A clear back-of-ID barcode photograph can also be read by the existing photo decoder. **Scan truck VIN barcode (optional)** supplies the arriving truck's barcode value. Both onsite photos remain mandatory.
4. Press **Submit Photos**. The app shows the **Safe Load QA Checker** popup with percentage and stage. These are server-reported WORKFLOW milestones, not identity-confidence scores, elapsed-time predictions or a timer pretending to review an image. At 0% the upload is not yet acknowledged; 10% received/assignment check, 25% image checks finished/license extraction, 55% license extraction finished/VIN read, 75% comparison, 90% evidence/custody save, 100% completed decision. Polling only retrieves progress; it does not advance the percentage. This release uses the existing local OCR/barcode engine, not a new cloud vision/biometric service.
5. Successful QA shows **CONFIRMED · CLEAR - FOR TRANSIT** in green and the persistent **Confirmation # SL-...**. The shipment moves to in_transit. Confirmation numbers are generated server-side, unique, stable on repeated reads and included in the release custody snapshots. Broker-authorized exceptions also receive a confirmation with their manual release method preserved.
6. Rejected QA shows **REJECTED · DO NOT RELEASE**, reasons and **Call Broker**. The software saves both photos/extracted fields and notifies the broker as before. The warehouse cannot authorize an exception. The broker reviews the evidence and independently verifies the driver/truck before authorizing release in desktop. The app updates from the shared backend.

A load already rejected BEFORE this update still requires broker resolution. A readable new scan does not erase a previous rejection or automatically release a held shipment. Use a NEW fictional load for the automatic-confirmation scenario, and the existing rejected load for the broker-authorization scenario.

## What the barcode does and does not prove

US AAMVA PDF417 barcodes commonly encode name, license number, issuing jurisdiction, expiration and birth date; fields vary by card/version. AAMVA standard: https://www.aamva.org/getmedia/81af105d-8b1b-45e1-aa46-f1800a259ed1/AAMVADLIDCardDesignStandard2025.pdf . A state field reference is https://dds.georgia.gov/document/document/barcode-sheet-printed-after-october-2012pdf/download .

A live scan supplies structured identity data instead of guessing a printed layout. If a readable PDF417 in the submitted photograph disagrees with that live scan, release is rejected. VIN photo/scan contradictions also reject. Empty, malformed, incomplete, expired, wrong-driver or wrong-VIN data does not automatically pass. Same-identity valid renewed expirations and broker review of changed license identities follow the existing v0.19.6 rules.

Live scan data and camera timestamps are client-declared observations; a barcode is not a cryptographic proof that an authentic card belongs to the arriving person or that the scan and photo depict the same physical object. No DMV check, facial recognition, liveness or VIN ownership validation is performed. A confirmation number records this workflow's release decision, not government authentication. The broker can still independently review both photos.

DOB is shown in the transient barcode preview when present. The app clears scan state after successful submission, assignment changes and sign-out. Raw barcode and DOB are not separately saved in extraction records/custody summaries; required encrypted photographs may naturally contain the printed DOB. Full extracted license number remains encrypted and broker-restricted as before.

## Extraction improvements and limits

The reported errors were actual unreadable/ambiguous OCR fields, not a queue waiting for a human. This release adds a sparse-text OCR pass alongside the existing block-text pass and rotations, to better handle two-column ID layouts and separated VIN labels. It does not invent missing license numbers, names or VIN characters. Structured live PDF417 extraction is recommended when the front layout cannot be read. Capture straight-on, in focus and without glare; a VIN must contain exactly 17 valid characters. Test your physical device and real card layouts before a live pilot.

## Persistence and compatibility

The existing tables, prior migrations, seed/schema-upgrade code and Compose volume definitions are retained. Startup adds `safe_load_release_receipts`; additive SQL is in `backend/migrations/0198_safe_load_confirmation.sql`. Existing releases are not backfilled with made-up receipt timestamps or confirmations. They display a legacy-release note and retain their original custody history.

Progress records are bounded, short-lived and contain no identity data. They use the current single API-process Docker setup. A server restart loses progress display, not persistent evidence, receipt or release state; refresh the shipment. A future multi-worker deployment should use shared progress storage. Receipt creation, release and custody snapshots commit together. Failed network/server uploads retain the local photos for retry as in v0.19.7.
