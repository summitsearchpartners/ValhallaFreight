# v0.19.11 — Cropped ID photos and a simple back-photo workflow

## Current camera behavior

This release removes the confusing native/Google scanner and live-preview buttons from the phone workflow. Phones can read PDF417 barcodes, but this implementation now uses a **photo of the ID back** and the backend decoder instead of depending on device live-scanner behavior.

The earlier timed automatic photo check was not continuous document detection: it could fire before a card was positioned, then stop. This release removes that unreliable automatic attempt. **Capture is manual and guided.** No timer takes pictures while waiting for the card.

1. Tap **Take ID Front Photo**. Place the whole physical ID inside the outline, then tap **Take Photo**.
2. The app maps the actual guide rectangle through the center-cover camera preview into captured-image pixels and crops locally with Expo ImageManipulator. Only that ID region appears in the review screen and is kept on acceptance, rather than the entire camera view.
3. **Accept Photo** keeps the exact cropped image and returns to the load. **Retake** discards it and reopens the camera. Cancel/Android Back keeps no unaccepted image. The existing accepted-photo ownership/cancellation protections remain.
4. Take the truck VIN photo. Its capture remains manual and keeps the VIN photograph; no live barcode scanner is needed.
5. Tap **Take ID Back Photo** (optional but recommended when front OCR is unreliable). Keep all card edges and the entire PDF417 barcode inside the guide, then Take Photo → Accept Photo. The back uses the same ID crop and review flow.
6. Tap **Submit Photos**. The server reads the back-photo PDF417, extracts license identity/name/state/expiration and uses those fields in the existing QA against the dispatcher assignment. A readable back can supply structured data even when the front's printed layout cannot be read reliably.

Cropping is a real pixel crop, not merely a screen decoration. Mapping tests cover portrait and center-cover offset cases and invalid/clamped geometry. Preview/picture field-of-view differences and orientation on actual hardware still require a phone acceptance check. Retake if a required edge or barcode is cut off. There is no promise of automatic capture in this version.

## Release, rejection and evidence

Front ID and VIN photos remain required. Older clients and existing two-photo workflows remain compatible; the back photo is optional. If a back photo IS submitted, the server cannot silently ignore an unreadable or incomplete barcode: it rejects/holds for a clearer image or broker review. A readable front/legacy scan barcode that disagrees with the back barcode also holds the shipment.

All submitted front/back/VIN images are encrypted in document storage and linked to the evidence attempt. Authorized brokers see the back as a third image under **Onsite evidence & extracted data**, alongside extracted fields, reasons and existing attempts. Custody snapshots include its encrypted-file hash/reference; exported paths stay redacted. Scoped photo access includes only authorized manufacturer/broker/Super Admin users, with designated Muse access limited to actual Muse-booked loads.

Normal matching still produces the existing confirmation number and Clear - For Transit. Rejection still notifies the broker and displays the callback contact. Previously rejected loads still need broker resolution; a clearer back image does not erase an earlier rejection. Card fields do not authenticate a face, DMV record or truck ownership.

The app checks backend support before uploading a back photo. If an older backend would ignore the third file, submission is blocked with an update/rebuild message and the phone retains its photos for retry.
