# Valhalla Freight v0.14.0 — Manufacturer Customers & Verified Portal Access

## What changed

The manufacturer's company workspace is separate from the customer records it adds. Both Manufacturer and Manufacturer Admin can create and manage their own customers under **Customers**. The manufacturer's own company no longer appears in that list. Customers are linked to their manufacturer through `customers.manufacturer_id`; another manufacturer cannot access their freight, contacts, locations or customer settings. Existing company records and legacy freight stay intact. Quote Studio and shipment creation continue to support the original company and its new customers.

Creating a customer record does **not** create a login. Only **Valhalla Freight Admin** creates login accounts in **Administration → Users & Company Access**. Choose **Customer** and the appropriate customer portal. Manufacturer roles can be assigned only to manufacturer companies. The Companies popup and company account filter include accounts assigned to that company's customer portals.

## Open a portal as Valhalla Freight Admin

1. Sign in with a Valhalla Freight Admin account.
2. Open **Administration → Portal Access**.
3. Search the directory, filter by manufacturer, or use the previous/next buttons to cycle through company and customer portals.
4. Select a portal and enter **your own administrator password**. If enabled, enter a fresh authenticator code.
5. Click **Verify & open portal** and allow pop-ups for localhost if your browser requests it.

The portal opens in a separate window. Your identity and audit trail remain Valhalla Freight Admin; no customer password is used. The original admin window stays signed in. A banner identifies the customer and session expiry. Refresh works within the verified window. **Switch portal** returns to the selection screen for new verification. **End support session** revokes the grant and closes the support window, without signing out the main admin account.

Portal grants are bound to the real admin, one customer and a 15-minute expiry. Launch tickets expire in 60 seconds, are single use, and are stored only as hashes in PostgreSQL. The browser removes the ticket fragment after opening and keeps the resulting grant in that window's session storage. Direct portal URLs and forged company headers cannot bypass verification. Support tokens are rejected as normal API bearer tokens. Portal reads, edits and document routes all enforce the grant and selected customer. Disabled/demoted accounts lose super-user support access immediately.

User Activity records verification failures, successful verification, portal opening, API requests and session ending under the real administrator, including the selected customer. Passwords, codes, enrollment keys and tokens are excluded from activity records. Five failed verification attempts lock portal verification for five minutes; the ordinary admin workspace remains available.

## Google Authenticator

Optional Google Authenticator verification is available now for this portal-access workflow:

- Click **Set up Google Authenticator**, verify your admin password, scan the QR code (or enter the manual key), and confirm a generated code.
- Setup expires after 10 minutes. Once confirmed, opening any portal requires your password plus a fresh six-digit code. A used code cannot be replayed; wait for the next code after enrollment or a successful launch.
- **Manage authenticator** lets the same administrator disable it with their password and a fresh code.
- Enrollment keys are encrypted with the existing integration-secret encryption mechanism. Keep your existing `JWT_SECRET_KEY` / `INTEGRATION_SECRET_KEY` stable across upgrades.

This is additional verification for support portal access. The existing primary login flow remains unchanged.

## Data-preserving local Docker upgrade

Use your existing installation directory and Compose project name, and retain your existing `.env`. A new directory/project name can select a different named Docker volume and make existing data appear missing.

Before upgrading, a PostgreSQL backup can be made with:

```powershell
docker compose exec -T db pg_dump -U valhalla_freight -d valhalla_freight -Fc -f /tmp/valhalla-before-v014.dump
docker compose cp db:/tmp/valhalla-before-v014.dump ./valhalla-before-v014.dump
```

Replace project files with this release, preserving `.env`, then run:

```powershell
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 backend
```

Open http://localhost:5173 and refresh the browser. No database reset or volume deletion is required. Do not run `docker compose down -v` or the reset script. The release preserves the Compose volume names and prior migration statements. Startup creates the two new support-security/session tables and adds the nullable indexed manufacturer ownership link to existing customer records. Repeated startup is safe. Existing customers are not automatically reclassified, merged, reassigned or deleted; existing root company logins and freight remain available.

## Acceptance checks

- Manufacturer A: Customers excludes its own company; add a customer and edit its contacts/locations. Manufacturer B cannot see that customer. No login appears until a Valhalla Admin explicitly creates it.
- Valhalla Admin: assign a Customer login to the new customer; sign in to confirm the correct portal. Manufacturer login roles are unavailable for child customer portals.
- Valhalla Admin: search/cycle portals, verify a password, open two different customer windows, refresh each, inspect customer data and User Activity, and end a support session. The main admin session remains usable.
- Enable Google Authenticator and test a fresh code, a wrong code and a replayed code. Confirm direct `/portal?company_id=...` access requires a verified support grant.
- Confirm existing company branding, My Profile, System Settings, Pricing Engine, Quote Studio, multiple freight classifications, shipment booking and BOL numbers remain available.
