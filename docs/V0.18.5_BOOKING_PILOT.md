# v0.18.5 — Freight film and booking workflow

## Changes

- Replaced the login background with close semi-truck footage and an Oregon highway aerial, using credited Pexels recordings. Includes a crossfade, cleaner color treatment, local MP4/WebM and poster. Pause, reduced-motion, mobile and failed-media fallbacks remain.
- Google Places is optional for booking. Use **Enter manually**, fill the full street address/city/state, and check the confirmation for each facility. Editing the facility resets that confirmation. Saved locations and Google suggestions still work.
- ZIP-only quoting remains unchanged. Full ship-from and ship-to addresses are still required for the BOL, carrier pickup and delivery. Manually confirmed addresses are identified as manual; they are not represented as Google verified. The backend rejects blank addresses and ZIPs that differ from the rated lane.
- Total package count is calculated directly from the quote freight lines. The backend fills it when omitted and rejects mismatches, including later edits on quoted shipments. Each freight class remains separate.
- Fixed Dayton electronic BOL line/total weight to multiply per-unit weight by quantity, matching the vendor schema's total-weight fields. Printed BOL weights and package rows use the same freight quantities.
- Dayton responses must report PASS or WARNING to count as accepted. FAIL or missing acceptance produces a booking error. Sandbox submissions display **test submitted**, never live submitted.
- Dayton shipment records now show evidence for carrier request, carrier tracking, delivery, POD/delivery receipt attachment and customer invoicing. Manual delivery timestamps and outbound test requests do not mark live carrier evidence complete. Document attachment means a file exists, not that its contents were independently verified.
- Broker and Super Admin shipment records can **Issue customer invoice** using the recorded customer charge and configured Net payment terms. Repeated clicks reuse the existing invoice. This records a local invoice, not an email, payment, or accounting-system sync. Manufacturers can view their invoices but cannot issue them.

Manufacturer financial privacy, broker/admin tools, Muse rates and approval, roles, company scoping, freight classifications, quote booking, and BOL generation remain.

## Update without losing data

Keep the same installation directory, Docker Compose project name, existing .env and volumes. Back up the database, copy application files over the existing installation, then run:

```sh
docker compose up -d --build
```

Open http://localhost:5173. Do not delete volumes or run reset scripts. There are no schema changes or migration edits in this release; the manual confirmation flag lives in existing address JSON.

## Optional Google address search

Manual confirmation works without a key. To enable suggestions, place your Google Maps browser key in `VITE_GOOGLE_MAPS_API_KEY` in the root .env, enable Maps JavaScript API and Places API (New) plus billing in that Google project, and allow your actual browser origin (for local testing, http://localhost:5173/*) in the key's HTTP-referrer restrictions. Recreate the frontend with `docker compose up -d --build frontend`. No Google account credentials are bundled.

## Controlled pilot acceptance

The environment used for this release has no live Dayton credentials and cannot certify a live freight movement. Local tests and mock carrier responses are not evidence that Dayton production accepted a shipment.

Before moving real freight:

1. Configure the correct company's Dayton account and sandbox credentials in Integration Hub; run the authentication and rate tests. Authentication alone is not an end-to-end pass.
2. In coordination with Dayton, test a quote and electronic BOL with multiple freight lines. Compare package counts, total weights, addresses, payment terms and requested services against the carrier response. Review any WARNING response. Confirm a live pickup/booking reference separately from an electronic BOL acceptance.
3. Prove carrier tracking on that shipment using an authorized test/reference PRO. Confirm delivery came from the carrier, not a manual timestamp.
4. Retrieve/review the delivery receipt or POD with Dayton and attach it to the shipment. Automated Dayton POD ingestion is not implemented by this release.
5. Issue the customer invoice and verify the customer-facing amount and due date. Test carrier invoice ingestion/audit separately in Finance Center. Carrier invoice retrieval, accounting sync, payment collection and invoice emailing are not proven by local issuance.
6. Record results and obtain carrier approval before using production. Retain simulated/test labels until actual live evidence is available.

The application-level checks are described in RELEASE_CHECKS.md. Docker/container startup itself requires local testing because Docker was unavailable in the build environment.
