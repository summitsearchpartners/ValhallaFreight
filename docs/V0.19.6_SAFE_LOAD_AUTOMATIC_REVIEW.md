# v0.19.6 — Automatic onsite photo QA and broker evidence review

## Update the desktop and phone projects together

Keep your current `.env`, PostgreSQL volume and document volume. Make a normal backup before replacing application files. Copy the contents of the ZIP's inner `ValhallaFreight` folder into `C:\GitHub\ValhallaFreight`, including `safe-load-mobile`. Do not copy an older node_modules folder over the new mobile project.

Stop the old Expo/Metro PowerShell window with Ctrl+C. Rebuild desktop services:

```powershell
Set-Location C:\GitHub\ValhallaFreight
docker compose -p valhallafreight up -d --build
```

Then start the mobile source in a separate PowerShell window:

```powershell
Set-Location C:\GitHub\ValhallaFreight\safe-load-mobile
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-SafeLoad.ps1 -ComputerIP 192.168.1.195
```

Scan the NEW QR code using Expo Go SDK 58 on Android. In Safe Load use server `http://192.168.1.195:8000` and the existing manufacturer login. Confirm the header says **App v0.19.6**. If it does not, close the old Expo project and scan the new code. Keep Docker and Metro running. Refresh the desktop with Ctrl+F5. Existing local-subnet firewall rules for 8000/8081 still apply.

This source ZIP has no copy of your live database or uploaded identity documents. Updating it retains those existing local Docker volumes. Startup adds two tables using the existing metadata upgrade mechanism; the additive PostgreSQL SQL is also supplied as `backend/migrations/0196_safe_load_automation.sql`. Prior migrations are unchanged. **Never use `docker compose down -v`.**

## Save the broker callback once

Sign into the appropriate **Broker Admin** account, open **My Profile → Safe Load call contact**, enter a monitored contact name and phone including area code, and press the page's single **Save changes** button. This is a company setting shared with authorized broker users. Regular Brokers can read it but cannot change it. Manufacturer accounts cannot edit broker contacts. Super Admin can set a selected company's contact or the platform fallback in My Profile.

Active loads resolve their callback from the responsible broker's profile automatically. A genuine Muse booking uses the designated Muse broker; otherwise a Super Admin customer-to-broker assignment, broker-owned customer parent or explicitly configured company determines ownership. A company's existing shared contact takes priority over earlier per-shipment contacts. Legacy shipment contacts are retained as fallback when no shared profile exists; clearing an existing shared profile deliberately disables that company's fallback. The old per-shipment API remains for compatibility, but its edit form has been removed.

Missing callback setup does not discard evidence: warehouse submission uploads both photos and holds/rejects release for broker review. Broker Admin must configure a valid contact before release authorization.

## Warehouse: camera, camera, submit

1. Open an unreleased load; view the dispatcher ID photo, driver name and truck VIN already on file.
2. Tap **Take driver ID photo** and photograph the current physical ID with readable printed fields. A sharp ID-back PDF417 photo is supported when it contains all required identity fields. Tap **Take truck VIN photo** and photograph the arriving truck's VIN label. Both are native camera captures in the mobile app; the phone flow has no saved-photo picker.
3. Review the previews and press **SUBMIT · VERIFY & RELEASE**. There is **no warehouse visual-match checkbox**, driver confirmation or manual exception approval.
4. The server reads the uploaded images locally, checks license identity/state, driver name, valid expiration and exact VIN. A first matching arrival releases the hold, records pickup/in-transit events and displays **CONFIRMED — RELEASED FOR TRANSIT**. Failed/unreadable data keeps the freight held, records a critical broker notification and opens **REJECTED — DO NOT RELEASE** with the shared broker contact and **Call broker** action.

A rejected load stays held until broker resolution, even if a subsequent upload matches. Capture controls remain available to supply better evidence. New dispatcher assignments invalidate old captured data and require a fresh submission. Each signed-in employee should use an individual login for meaningful actor attribution.

## Broker: onsite evidence and authorization

Open **Notifications → Review rejection & authorize release**, or the load in Safe Load. The broker view shows the dispatcher record and **Onsite evidence & extracted data**: both submitted ID/VIN photos (click to enlarge), submission account/time/revision, rejection reasons and extracted field comparisons. Select earlier evidence attempts to inspect preserved failures. The comparison heading refers to the current dispatcher record; use the revision-specific custody snapshots when reviewing an older assignment.

The full extracted license number is available only through an authenticated, shipment-scoped broker/Super Admin endpoint and is encrypted at rest. Warehouse summaries mask it to the last four characters. Photo endpoints are authenticated, scoped and `no-store`; both photos remain encrypted in document storage. Read/view events are recorded. Existing attempts created before v0.19.6 still show their photos but have no fabricated extraction record.

The broker independently calls/verifies the carrier/warehouse, reviews both current onsite pictures and the rejection reasons, checks the driver/truck/evidence confirmations and records callback/verification notes. **Confirm verified driver & release for transit** authorizes the current rejected assignment. Manufacturers cannot invoke it. The warehouse app polls while foregrounded and refreshes when returning from a phone call; release becomes visible without restarting. Desktop uses live updates. No SMS, external email or push service is configured by this update; the notification is in the software.

## Renewed or reissued licenses

The system compares identity fields, not card artwork. Common suffix/punctuation and optional middle-name differences are normalized. A later, valid expiration with the same license number/state and matching first/surname can pass as a renewal. A different license number, state, mismatched name, expired document, ambiguous data or unexpected earlier expiration holds the load. The broker must explicitly acknowledge reviewing a possible reissued/changed license when authorizing that exception. The original dispatcher record, failed automatic decision and images are retained; authorization does not rewrite them.

OCR/barcodes extract document data and compare it to the assignment. They **do not authenticate the physical person, perform facial recognition/liveness, query DMV records or verify ownership of a VIN**. Matching document fields are not proof of identity. Unfamiliar layouts, glare, blur or partial images can require broker review. Rotated OCR retries improve sideways images but do not guarantee every license layout can be read. Do controlled device acceptance tests before relying on this workflow for live freight.

## Custody and persistence

Encrypted onsite photos, structured extraction results, authenticated operator IDs, declared device capture times, server receipt times, assignment changes, QA results, broker decisions and release transitions remain linked to the shipment. Shared contact changes generate snapshots for active affected loads. Full extracted license numbers are encrypted separately and omitted from snapshot summaries. The existing append-only hash chain and export remain intact. This is an application audit trail, not an externally notarized record; retain backups and an appropriate document-retention policy. Old custody entries are not changed or backdated.
